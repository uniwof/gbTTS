## Design objections  

| # | Concern | Reasoning | Suggested alternative |
|---|----------|-----------|------------------------|
| D1 | **Using a layered, `WS_EX_NOACTIVATE` ball as the sole UI** – while it avoids stealing focus, it also prevents standard WinForms controls (e.g. context menus, tooltips) from receiving mouse events unless they are also `NOACTIVATE`. The current design creates a custom `ContextMenuStrip` that is owned by the ball; on some DPI changes the menu can appear behind other windows or lose mouse capture. | Users may miss the voice‑pack menu or settings because the menu disappears when the ball moves or the DPI changes. | Create a separate *invisible* top‑level window (message‑only) that owns the menus, or use `WS_EX_TOOLWINDOW | WS_EX_TOPMOST` without `NOACTIVATE` and explicitly call `SetWindowPos` with `SWP_NOACTIVATE` when showing the ball. |
| D2 | **Polling timer (300 ms) for foreground tracking** – the new `SetWinEventHook` replaces it, but the old code still exists in the repo (not shown). If both run, they can race and cause the “last external window” to be wrong. | Inconsistent behavior when the user quickly switches apps. | Remove the polling timer entirely; rely solely on the WinEvent hook. |
| D3 | **Hotkey registration on a `NativeWindow` with `HWND_MESSAGE`** – message‑only windows do not receive `WM_HOTKEY` unless the thread has a message pump. The code likely creates the window on a thread‑pool thread without a pump, causing the hotkey to be lost after a handle recreation. | Users report hotkeys stop working after a window resize or after the app is minimized. | Register the hotkey on the main UI thread (the hidden Form) or create a dedicated STA thread with a `Application.Run()` loop that hosts the `NativeWindow`. |
| D4 | **UIA timeout strategy (3 s first call, 1.5 s later)** – this is arbitrary and may be too short for heavy browsers (Chrome, Edge) that lazily build the accessibility tree. The user may see “不支持朗读” even though the app could succeed after a longer wait. | Low‑end PCs are more likely to hit the timeout. | Expose a configurable timeout (e.g. 5 s) and cache the “warm‑up” state per process, so the first call can be longer but subsequent calls are fast. |
| D5 | **`Result` objects carry a `who` string that includes a `<zh>` placeholder** – this mixes UI strings with internal diagnostics, making localisation harder. | Future localisation or logging to a remote server becomes messy. | Separate UI‑visible strings from internal identifiers; keep `who` as a pure process/class identifier. |
